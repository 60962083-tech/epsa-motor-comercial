# HU-001: Consultar disponibilidad compartida

## Endpoint

`GET /api/inventario` requiere `Authorization: Bearer <token>`. Los roles permitidos son Gerente, Administradora y Vendedor. PostgreSQL vuelve a comprobar que el usuario y su rol estén activos antes de responder.

Filtros opcionales y combinables: `codubi`, `codmod`, `estado`, `color`, `codtte`, `codepr`, `limite` y `offset`. Los códigos deben ser IDs bigint positivos. `limite` va de 1 a 100 y por defecto es 50; `offset` es un entero no negativo y por defecto es 0. Un filtro válido sin coincidencias responde `200` con `items: []`.

Ejemplo: `GET /api/inventario?codubi=2&codmod=4&estado=Disponible&limite=25&offset=0`.

## Respuesta

```json
{
  "ok": true,
  "data": {
    "items": [
      {
        "coduni": "21",
        "modelo": { "codmod": "4", "nommod": "Modelo ejemplo" },
        "color": "Azul",
        "ubicacionConfirmada": { "codubi": "2", "nomubi": "Comas", "tipubi": "Sede" },
        "movimientoActivo": {
          "codmub": "7",
          "estado": "En transito",
          "destino": { "codubi": "3", "nomubi": "FIVESA" }
        },
        "techo": null,
        "preparacion": null,
        "situacionComercial": "No disponible"
      }
    ],
    "total": 1,
    "limite": 50,
    "offset": 0,
    "resumen": {
      "unidadesIdentificadas": 1,
      "cantidadPendienteIdentificacion": 0
    }
  }
}
```

Los contadores de `resumen` son globales y no cambian al filtrar o paginar: unidades identificadas cuenta filas reales de `unidad`; pendiente suma por compra `greatest(cancom - unidades asociadas, 0)` únicamente si existe un registro en `factura_compra` y `factura_compra.cantidad_motos = compra.cancom`. HU-034 deja las compras sin factura en `Pendiente de factura`; HU-002 exige factura recibida y cantidades coincidentes antes de identificar unidades, y rechaza discrepancias con `PT411`. Por eso se excluyen compras sin factura y facturas discrepantes. No se crean ni cuentan motos ficticias. El `total` sí cuenta los resultados del filtro antes de paginar.

Durante un movimiento activo, la ubicación confirmada sigue siendo `unidad.codubi` (origen hasta la recepción HU-003) y el destino aparece por separado. La RPC hace un `LEFT JOIN` set-based al movimiento activo, cuya unicidad por unidad garantiza el índice parcial de HU-003; no consulta el historial una vez por unidad. El endpoint no infiere ni modifica la situación comercial desde separaciones o ventas.

La RPC `public.hu001_consultar_inventario` es `SECURITY DEFINER`, usa `search_path` vacío y solo se puede ejecutar por `authenticated`. La ruta no concede permisos directos a las tablas. La respuesta omite series de motor/chasis, notas internas, compras, facturas, clientes, ventas, separaciones, costos y datos de autor.

## Índices

La migración reutiliza `ix_unidad_ubicacion` de HU-026 para `codubi` y crea índices en `unidad.codmod`, `unidad.codtte` y `unidad.codepr`, que son referencias selectivas disponibles como filtros. No crea índices en `coluni` o `estcomuni`: ambos valores suelen tener baja cardinalidad y no hay evidencia de distribución que justifique su costo de escritura.
