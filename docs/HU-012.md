# HU-012 / EMT-72: consulta pública y administración de modelos

## Despliegue

Aplicar `supabase/migrations/202610070002_hu012_modelos_publicados.sql` sobre el esquema compartido antes de desplegar el backend. No requiere HU-002 ni HU-007. Configurar `SUPABASE_URL` y `SUPABASE_ANON_KEY` (clave pública anónima, nunca service_role).

La migración inicial crea una RPC de lectura sin parámetros, ejecutable por anon y authenticated. La migración administrativa pendiente `202610100003_hu012_admin_modelos.sql` agrega RPCs seguras para mantener modelos e imágenes. Las tablas siguen sin CRUD directo para `anon` ni `authenticated`; las operaciones de administración pasan por funciones `SECURITY DEFINER`, con `search_path` vacío y comprobación del rol en servidor.

## Contrato público

`GET /api/modelos`, sin Bearer token. Los encabezados de autenticación del visitante no se envían a Supabase. No admite parámetros de consulta; cualquier parámetro (incluidos estado, estmod, select u or) responde 400. No hay endpoints de escritura ni de administración en esta subtarea.

Respuesta 200: `{ "ok": true, "data": [...] }`. Cada ficha contiene exclusivamente:

- `codmod`: ID BIGINT como string.
- `nommod`, `marmod`, `desmod`, `carmod`: nombre, marca, descripción y características existentes.
- `imagenes`: objetos `{ "urlimo": "...", "ordimo": 1 }`, solo imágenes con `estimo = true`, ordenadas por ordimo y codimo. Sin imágenes activas, devuelve `[]`.

Las fichas se ordenan por nombre y código y solo aparecen si tienen al menos una imagen activa. La ficha individual HU-009 aplica el mismo criterio. Los modelos publicados incompletos que ya existan quedan ocultos. Sin modelos disponibles devuelve una lista vacía. Los errores internos responden 500 sin detalles de BD. Las respuestas llevan `Cache-Control: no-store` para evitar conservar fichas despublicadas en caché HTTP. El frontend deberá consultar nuevamente para actualizar una pantalla ya abierta.

## Administración pendiente

Solo Gerente y Administradora pueden usar las rutas administrativas, con Bearer token:

- `POST /api/modelos` crea un modelo; por defecto queda en `Borrador`. Si se envía `estmod: "Publicado"`, la RPC valida la ficha y exige una imagen activa.
- `POST /api/modelos/:id/imagenes` agrega una referencia activa `{ "urlimo": "/images/modelos/3/principal.png", "ordimo": 1 }`.
- `PUT /api/modelos/:id/imagenes/:codimo` actualiza referencia y orden.
- `PATCH /api/modelos/:id/imagenes/:codimo/estado` activa o desactiva una imagen. No permite desactivar la última imagen activa de un modelo publicado; no existe borrado físico.
- `PATCH /api/modelos/:id/estado` publica solo después de validar tipo, nombre, marca, descripción, características e imagen activa.

`urlimo` admite una ruta bajo `/images/` o una URL HTTPS válida. Las rutas son referencias; no suben ni crean archivos. El flujo de fotos sigue siendo: fuente externa → `scripts/descargar-imagenes.mjs` → `frontend/public/images` → Git → Netlify. Antes de agregar una referencia, el archivo debe existir en esa carpeta y desplegarse con el frontend. No se usa Supabase Storage. `premod` puede ser `null` y `colores` puede ser `[]` al publicar.

La respuesta administrativa `GET /api/modelos/admin` incluye todas las imágenes del modelo con `codimo`, `codmod`, `urlimo`, `ordimo` y `estimo`, de modo que también se puedan volver a activar. El catálogo público solo recibe imágenes activas.

## Alcance y límites del esquema

Para ocultar un modelo basta con cambiar su estmod a `No publicado` mediante el flujo administrativo correspondiente; la siguiente consulta lo excluye sin borrar modelo, imágenes ni referencias históricas. EMT-72 no implementa ese flujo administrativo.

En HU-012, `estimo = true` se toma como imagen activa y autorizada para publicación. El esquema no aporta otra evidencia de autorización. Tampoco representa precios por techo/configuración. No se inventan precios universales ni almacenamiento de archivos.

## Verificación

Revisión del 7 de octubre de 2026: el esquema local no concede SELECT de tabla ni columna a anon en modelo/imagenmodelo; los tests comprueban los permisos efectivos y que la lectura directa falla, incluso solicitando columnas concretas o estados internos. No se cambiaron grants ni RLS. Todos los modelos publicados del fixture tienen al menos una imagen activa; esto no implementa la validación administrativa de publicación ni acredita autorización de las fotos.

Auditoría de Supabase ejecutada y reportada por el usuario el 7 de octubre de 2026: ambas tablas tienen RLS habilitado, FORCE RLS deshabilitado y ninguna policy; anon tiene SELECT de tabla/columnas. Por tanto, RLS aplica default-deny a la lectura directa de anon y explica las listas vacías observadas por REST. La RPC es SECURITY DEFINER y anon/authenticated tienen EXECUTE. No es necesario modificar grants ni RLS. Se conserva `docs/HU-012-auditoria-permisos.sql` como consulta de solo lectura para futuras verificaciones.

Un test adicional reproduce esa configuración en PostgreSQL local, con datos publicados e internos presentes: anon obtiene listas vacías de ambas tablas y la RPC sigue exponiendo únicamente los modelos publicados e imágenes activas. Los grants y RLS del test se aplican exclusivamente a la BD efímera; no se modificaron migraciones ni Supabase remoto.

`npm test` incluye pruebas HTTP y PostgreSQL local (PGlite) con HU-026 y HU-034: publicación, estados internos ocultos, filtros rechazados, consulta anónima, proyección de campos, imágenes activas, administración, errores y despublicación conservando referencias. `npm run build` verifica TypeScript. Las pruebas locales no sustituyen la validación del esquema/permisos del Supabase remoto ni aplican la migración allí.
