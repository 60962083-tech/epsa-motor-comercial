# HU-014 — Registrar manualmente un interesado

## Preparación

Aplicar `supabase/migrations/202610090001_hu014_registro_lead_manual.sql` sobre el
esquema existente, después de HU-026 y HU-007. No crea nuevamente `lead` ni
`seguimientolead`, no carga datos comerciales y no requiere dependencias nuevas.
El esquema de referencia inspeccionado es `tests/fixtures/esquema-base.sql`:
`modelo.codmod`, `usuario.codusu`, `canalwhatsapp.codcwa`, `sede.codsed` y
`cliente.codcli` son PK bigint. La migración se verifica localmente con PGlite;
no se aplica automáticamente a Supabase remoto.

Después aplicar `supabase/migrations/202610100001_hu014_modelo_publicado.sql`.
Esta corrección reemplaza únicamente la RPC para exigir un modelo Publicado;
no modifica la migración anterior, los datos ni los permisos existentes.

## Endpoint y contrato

`POST /api/leads`

Headers:

```text
Authorization: Bearer <access_token>
Content-Type: application/json
```

Roles: **Gerente, Administradora y Vendedor**. Reutiliza `autenticar`,
`exigirRoles` y `res.locals.db`. La RPC también comprueba identidad y rol activos
desde `auth.uid()` y `hu026_rol_actual()`. Nunca utiliza service_role.

| Campo | Regla |
| --- | --- |
| `nomlea` | Texto obligatorio, máximo 150 caracteres; espacios normalizados |
| `tellea` | Texto obligatorio; 7–15 dígitos; admite separadores, paréntesis y `+` inicial |
| `codmod` | ID obligatorio de modelo comercial existente con estmod=Publicado, independiente del inventario |
| `canlea` | Texto obligatorio, máximo 50 caracteres; WhatsApp y Presencial normalizados |
| `estlea` | Obligatorio: Nuevo, Contactado, En seguimiento o Cerrado |
| `codusu` | HTTP admite ausencia/NULL y lo transmite como NULL; la RPC lo exige mientras ausencia esté inactiva. Usuario y rol activos de Gerente/Administradora/Vendedor |
| `fecprosle` | HTTP admite ausencia/NULL; la RPC lo exige para activos con ausencia inactiva. Si se informa, fecha ISO con zona horaria, no pasada. En Cerrado debe ser NULL u omitirse |
| `collea` | Opcional: Rojo, Azul, Amarillo, Verde, Negro o NULL; entrada sin distinción de mayúsculas |
| `orilea` | Origen comercial opcional, máximo 30 caracteres; desconocido = NULL; Manual se rechaza |
| `codsed` | Obligatorio para Presencial; si se envía, debe existir en sede |
| `codcwa` | Obligatorio para WhatsApp; si se envía, debe existir en canalwhatsapp |
| `obslea` | Texto opcional, máximo 10000 caracteres; espacios normalizados |
| `nueva_oportunidad` | Boolean opcional, predeterminado false |

IDs bigint como strings; también se aceptan números enteros seguros de JSON.
No se aceptan campos desconocidos: `coduni`, correo, creador, `codcli`,
`tipreglea`, modo ausencia, etc. no son parámetros de creación.
El modelo debe estar Publicado; No publicado, Borrador o inexistente devuelve
404 con el mensaje "El modelo no existe o no está publicado".
No se inventa un catálogo de canales u orígenes; otros canales no vacíos se admiten. Se verifica existencia de sede
y canal WhatsApp, sin añadir reglas de estado no confirmadas para estos catálogos.

El teléfono se guarda solo con dígitos, sin separadores ni `+` inicial.
`+51 (987) 654-321` y `51987654321` coinciden. No se infiere país ni se añade
prefijo: un teléfono local y otro con prefijo no se equiparan automáticamente.
El color es una preferencia del lead, no `unidad.coluni`.

## Coincidencias y 14 días

La RPC normaliza el móvil tanto de la petición como de leads históricos.
Entre leads Nuevo, Contactado o En seguimiento del mismo teléfono, calcula la
última actividad como máximo de `fecreglea` y los seguimientos realizados.
`fecinisle` ya es timestamptz; si existe `horsle`, se combina con el día de
`fecinisle` en America/Lima y se toma el mayor de ambos instantes para no perder
actividad. `fecprosle` es una cita futura, no actividad realizada.

Si la actividad es **posterior** a ahora menos 14 días, devuelve **409**:

```json
{
  "ok": false,
  "message": "Ya existe una oportunidad activa para este contacto",
  "coincidencia": { "codlea": "12", "codmod": "1", "estlea": "En seguimiento" }
}
```

No crea ni modifica nada en ese caso. Se devuelve la coincidencia más reciente,
sin nombre, teléfono ni observaciones. Si el ciclo anterior está Cerrado o
Convertido, o la última actividad tiene exactamente 14 días o más, permite otra
oportunidad. Un lead antiguo con seguimiento reciente sigue produciendo 409.

`nueva_oportunidad: true` omite expresamente el bloqueo por coincidencia y crea
otro lead, conservando el anterior. No omite ninguna validación de datos,
referencias o permisos. El teléfono no es UNIQUE. Un advisory lock transaccional
por teléfono serializa registros simultáneos de esta RPC.

## Trazabilidad y transacción

`hu014_registrar_lead_manual` inserta lead y seguimiento inicial en la misma
transacción. El seguimiento usa `tipsle='Registro manual'`, `dessle=obslea`,
hora de Lima y `fecprosle` de la petición. También conserva una actividad inicial
para Cerrado, aunque no tenga próximo contacto. Si falla el seguimiento, se
revierte el lead completo.

`lead.codusu` es el responsable; `lead.codcrelea` identifica al creador resuelto
en la BD mediante auth.uid(), sin parámetro de identidad enviado por frontend.
`seguimientolead.codusu` identifica a quien realizó la actividad inicial.

Canal (`canlea`), origen comercial (`orilea`) y tipo de registro (`tipreglea`)
son distintos. HU-014 siempre escribe Manual; el nuevo atributo también permite
Web para una HU futura. No se reclasifican registros históricos.

`lead.codcli` tiene FK nullable a cliente.codcli y siempre queda NULL al crear.
No se crea cliente ni se implementan separación, venta o conversión.

## Modo ausencia / dependencia HU-035

No existe una fuente backend de modo ausencia en el repositorio. La configuración
en frontend es local y no concede excepciones en esta API.
El flujo normal exige responsable y próximo contacto para estados activos.

La función privada `hu014_modo_ausencia_activo()` retorna false y no puede
ejecutarse ni modificarse desde authenticated/anon. Aísla el punto en que HU-035
deberá consultar configuración confiable del servidor. La rama de excepción de
la RPC queda preparada para Nuevo, responsable NULL y próximo contacto NULL,
sin seguimiento inicial; **no se puede activar hoy a través de este endpoint**.
La capa HTTP transmite `codusu` y `fecprosle` omitidos/NULL como parámetros NULL.
La RPC es la autoridad: con ausencia inactiva rechaza responsable NULL y cita
NULL en estados activos con PT400. Si HU-035 habilita la fuente server-side,
la RPC podrá forzar Nuevo, responsable NULL y cita NULL sin bloqueo previo de
HTTP. Las fechas informadas siguen validándose y Cerrado con cita no NULL sigue
rechazándose en ambas capas. No se implementaron configuración, reparto ni
notificaciones ni se acepta un boolean de ausencia enviado por frontend.

## Cambios de esquema y seguridad

- Lead: `orilea` admite NULL; agrega `codsed` FK sede, `collea`, `tipreglea`,
  `codcli` FK cliente y `codcrelea` FK usuario, todos nullable para históricos.
- CHECK de color, tipo de registro, estados y mínimos de los nuevos registros
  Manual. Se usan NOT VALID y alcance por tipo de registro para conservar datos
  anteriores; los nuevos INSERT/UPDATE sí se comprueban. No se aplica NOT NULL
  global a teléfono/modelo ni UNIQUE al teléfono.
- Seguimientolead: conserva todas sus columnas; agrega índice `(codlea,fecinisle DESC)`.
- Índice del teléfono normalizado para leads activos.
- RLS en lead/seguimientolead; revoca acceso directo a tablas y secuencias de
  PUBLIC/anon/authenticated. Políticas restrictivas impiden eludir la RPC.
- RPC SECURITY DEFINER con `search_path=''`, validación interna de identidad/rol,
  helpers privados y EXECUTE de la RPC solo para authenticated.

La conservación de históricos mediante NOT VALID sigue el comportamiento de
[PostgreSQL ALTER TABLE](https://www.postgresql.org/docs/current/sql-altertable.html).
Los locks usados siguen [PostgreSQL Explicit Locking](https://www.postgresql.org/docs/current/explicit-locking.html).

## Errores

Formato `{"ok":false,"message":"..."}`, con coincidencia mínima en 409.
Los mensajes SQL, tokens y detalles internos no se exponen.

| HTTP | Caso |
| --- | --- |
| 400 | Campos/tipos inválidos, campos desconocidos, teléfono/color/estado inválidos, Convertido, falta responsable/sede/canal receptor/cita, fecha pasada |
| 401 | Bearer ausente o sesión inválida/vencida |
| 403 | Rol no permitido o usuario/rol inactivo |
| 404 | Modelo, sede, canal WhatsApp o responsable inexistente; responsable inactivo/no habilitado |
| 409 | Mismo móvil, lead activo con actividad menor de 14 días y sin nueva oportunidad explícita |
| 500 | Error inesperado, sin detalles internos |

## Postman y verificación

Importar `docs/HU-014.postman_collection.json`; configurar API, Supabase URL,
anon key, credenciales de una cuenta QA y IDs reales. Iniciar sesión captura
`access_token`; las peticiones de registro heredan Bearer. Cambiar móviles de
prueba cuando corresponda. Repetir registro normal prueba 409; la petición de
nueva oportunidad prueba el consentimiento explícito para otro lead.

Ejecutar `npm test` y `npm run build`. Las pruebas API usan mocks; las de BD
usan PGlite y el esquema del repositorio, sin conexiones a Supabase real.
PGlite serializa una conexión; las pruebas de peticiones competidoras y retención
del lock no sustituyen una prueba de concurrencia con conexiones PostgreSQL reales.
