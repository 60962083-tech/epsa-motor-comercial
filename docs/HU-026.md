# HU-026 — Integración del backend y pruebas de aceptación

## Alcance implementado

- Alta, edición, consulta y activación/desactivación lógica de ubicaciones.
- Catálogo inicial de siete lugares sin inventar direcciones.
- Unicidad de nombre ignorando mayúsculas y espacios exteriores/repetidos. Las tildes se conservan.
- Sesión validada con Supabase Auth y autorización por usuario/rol activo.
- Gerente y Administradora gestionan; Vendedor consulta; anónimos no acceden al catálogo interno.
- Bloqueo de desactivación por unidades o movimientos pendientes/en tránsito, también al acceder directamente a la BD.
- Restricciones para no asignar unidades ni abrir movimientos en ubicaciones inactivas.

## Aplicar en el entorno de pruebas

La migración presupone las tablas del esquema que compartió el equipo; `tests/fixtures/esquema-base.sql` es una copia para pruebas, no una migración de producción.

1. Revisar y ejecutar `supabase/migrations/202610030001_hu026_ubicaciones.sql` con el SQL Editor administrativo de Supabase del entorno de QA.
2. La migración es transaccional y admite reaplicación. Si encuentra nombres que se vuelven duplicados, revierte: revisar los registros y sus referencias antes de fusionarlos. No elimina datos para resolver duplicados.
3. Sustituye las tres políticas conocidas para `anon`, habilita RLS en ubicacion y añade políticas de lectura/escritura. Revoca escritura de clientes en usuario y rol para impedir autoasignación de permisos; HU-007 debe administrar esos registros desde un proceso autorizado de servidor, sin devolver permisos de edición de roles al cliente.
4. Conserva las ubicaciones existentes y sus direcciones/estados. Completa los lugares que falten y corrige `Crossland Ancon` a `Crossland Ancón` conservando su ID si no existe ya la variante con tilde. Si ambas variantes ya existen, revisar su posible duplicidad manualmente; no se fusionan automáticamente.
5. Si ya existían traslados en curso representados de otra manera, identificarlos y actualizar `estmub` antes de habilitar la desactivación. Los registros preexistentes reciben `Finalizado` por compatibilidad con el esquema original sin estado.
6. Revisar que las cuentas de prueba existan en Authentication y que `usuario.uuidusu` apunte a sus IDs reales. Los INSERT de usuario no crean cuentas ni contraseñas en Auth. Comprobar el vínculo real de `codrol`, sin asumir que los IDs siempre son 1/2/3.

Este cambio no se aplica automáticamente a Supabase al iniciar la API. Debe desplegarse coordinadamente con el backend: la API nueva necesita la función `hu026_rol_actual` de la migración.

## Contrato HTTP

Todas las rutas requieren `Authorization: Bearer <access_token>` y, cuando hay cuerpo, `Content-Type: application/json`.

| Método | Ruta | Uso | Perfil |
|---|---|---|---|
| GET | /api/ubicaciones | Catálogo completo, incluidas inactivas | Los tres roles activos |
| GET | /api/ubicaciones?activo=true | Opciones para nuevos movimientos | Los tres roles activos |
| GET | /api/ubicaciones?activo=false | Catálogo inactivo | Los tres roles activos |
| POST | /api/ubicaciones | Crear | Gerente / Administradora |
| PUT | /api/ubicaciones/:id | Reemplazar nombre, tipo y dirección | Gerente / Administradora |
| PATCH | /api/ubicaciones/:id/estado | Activar o desactivar | Gerente / Administradora |

POST y PUT:

```json
{"nomubi":"Taller de prueba","tipubi":"Proveedor","dirubi":null}
```

Tipos almacenados: `Sede`, `Almacen` (almacén externo), `Proveedor` (fibrera). El frontend debe mostrar estas etiquetas comprensibles. Nombre: 1–120 caracteres tras normalizar espacios. Dirección: opcional, hasta 250 caracteres; vacía u omitida se guarda como null. PUT omitiendo dirección la deja en null.

PATCH:

```json
{"estubi":false}
```

La respuesta exitosa contiene `ok: true` y `data`; las escrituras también contienen `message`. Errores: `ok: false`, `message`. Estados: 200 consulta/edición/estado; 201 creación; 400 entrada inválida; 401 token ausente/inválido; 403 perfil no permitido; 404 ubicación inexistente; 409 duplicado o asignaciones pendientes; 500 fallo interno.

No se implementa DELETE: la baja es lógica y preserva referencias históricas. No se implementa el registro de movimientos de HU-003; esta entrega proporciona el catálogo y sus protecciones de integridad.

## Integración de movimientos (HU-003)

`movimientoubicacion.estmub` admite `Pendiente`, `En transito`, `Finalizado` y `Cancelado`. Los dos primeros bloquean la desactivación de origen y destino. El valor por defecto es `Finalizado` para conservar el comportamiento de un registro de movimiento ya realizado. El módulo de traslados debe enviar explícitamente `Pendiente` o `En transito` cuando corresponda.

Al finalizar un traslado, HU-003 debe actualizar también la ubicación de la unidad en una misma transacción de negocio. Cambiar `estmub` no mueve automáticamente la unidad. Los triggers de esta entrega bloquean las filas de ubicación al asignar unidades o abrir traslados, coordinándose con la desactivación; no reemplazan el flujo completo de HU-003.

## Pruebas para QA

Importar `HU-026.postman_collection.json`. Configurar localmente `api_url`, `supabase_url`, `supabase_anon_key`, `email`, `password`. No guardar tokens ni contraseñas en Git ni exportarlos con la colección.

Ejecutar primero **Iniciar sesión**: guarda el access_token en la colección. No hace falta construir una pantalla de login para probar el backend. Para cambiar de rol, cambiar email/password y volver a ejecutar esa petición. Renovar el token iniciando sesión otra vez cuando venza.

La petición Crear guarda `codubi` para Editar/Desactivar/Reactivar. Para comprobar duplicados, fijar un `nombre_prueba` en vez de usar el timestamp. Desactivar al terminar la ubicación creada, sin eliminar historial.

| Caso | Resultado esperado |
|---|---|
| Listar catálogo | Los siete lugares iniciales; direcciones desconocidas null |
| Crear Sede, Almacen y Proveedor | 201; aparecen en consulta de activas |
| Crear `Comas`, ` COMAS ` o `Puente  Piedra` cuando ya existen | 409 |
| Editar una ubicación usando el nombre de otra | 409 |
| Nombre vacío, tipo desconocido o dirección numérica | 400 |
| ID negativo, decimal o fuera de BIGINT | 400 |
| ID válido inexistente al editar/desactivar | 404 |
| Desactivar ubicación sin unidades/traslados activos | 200; desaparece de ?activo=true |
| Desactivar ubicación con unidad asignada | 409; sigue activa |
| Desactivar origen o destino con traslado Pendiente/En transito | 409; sigue activa |
| Finalizar/cancelar traslado y retirar unidades; desactivar | 200; historial permanece |
| Asignar unidad o abrir traslado con ubicación inactiva, incluso directo en BD | Rechazo PT422 |
| Vendedor consulta / intenta escritura | 200 / 403 |
| Token ausente o vencido | 401 |
| Usuario o rol inactivo | 403 |

Para las pruebas con unidades/movimientos usar datos de QA válidos con sus compras, modelos y usuarios; no insertar referencias ficticias en producción.

## Verificación automatizada y límites

`npm test` ejecuta pruebas HTTP con un cliente de Supabase simulado y pruebas SQL con PostgreSQL embebido (PGlite), cargando el esquema original y la migración real. No usa `.env` para conectarse a Supabase ni modifica datos remotos. Verifica catálogo, reaplicación, duplicados, roles, bloqueos e historial. Las pruebas embebidas no simulan múltiples conexiones concurrentes ni reemplazan la prueba de extremo a extremo en Supabase QA.

`npm run build` compila TypeScript. La validación final de tokens reales, políticas existentes adicionales y despliegue corresponde a QA tras aplicar la migración.
