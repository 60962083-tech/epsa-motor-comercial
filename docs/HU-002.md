# HU-002 — Identificación de unidades compradas

Implementa identificación parcial o completa por lotes atómicos sobre una compra de HU-034. Cada unidad se vincula a la compra original; motor y chasis son únicos. Identificar no recibe, prepara, libera ni entrega motos.

## Instalación

Aplicar las migraciones en orden: HU-026, HU-034 y `202610060001_hu002_identificacion_unidades.sql`. No volver a aplicar una migración antigua después de HU-002: sustituiría funciones o restricciones por su versión anterior. La nueva migración admite reaplicación sobre sus propios cambios.

No recrear el esquema base. La migración conserva compras y unidades existentes; si detecta compras con más fichas que cancom o series duplicadas tras normalizar, aborta para revisión sin fusionar fichas ni inventar valores. No completa colores nulos de fichas históricas; exige color en nuevas identificaciones mediante el trigger, sin imponer un NOT NULL que altere datos anteriores.

Usar la configuración y las cuentas de Supabase ya existentes. `npm test` ejecuta todas las pruebas y `npm run build` compila. No se añade ninguna dependencia ni se usa service_role. La aplicación consume el token actual mediante los middleware existentes.

## Factura: implementado y pendiente

La tabla `factura_compra` guarda un registro por compra con emisor, número, fecha de emisión, cantidad declarada de motos, usuario que lo registró y fecha de registro. La relación es `factura_compra.codcom → compra.codcom ← unidad.codcom`: una factura asociada a una compra corresponde a todas sus unidades. No se duplica la factura en cada ficha ni se usa obscom.

Emisor/número son información declarada y deben copiarse del documento recibido. No se impone un formato de RUC, una dirección o numeración inventada. No existe unicidad global de número, porque distintas empresas pueden usar la misma numeración. Este alcance vincula metadatos por compra; un registro canónico de un mismo documento repartido entre varias compras requiere modelado posterior si el equipo lo necesita.

**Pendiente para cerrar el criterio de adjuntar factura:** seleccionar almacenamiento privado, definir carga autenticada, tipo/tamaño de archivo, validación, vínculo del objeto almacenado con codfac y descarga autorizada. No se creó un bucket ni se guarda una URL arbitraria. La respuesta indica `archivo_adjuntado: false`; no representa una carga realizada. HU-002 no está completa respecto al archivo físico hasta implementar y verificar ese flujo.

## Estados y cantidades

1. HU-034 crea `Pendiente de factura`.
2. Registrar los metadatos de la factura recibida cambia a `Pendiente de identificación`, aunque todavía no se haya identificado ninguna moto.
3. Identificar parte de la compra conserva `Pendiente de identificación`.
4. Al llegar exactamente a cancom, cambia a `Identificada`.

El listado de pendientes de HU-034 ahora incluye ambos estados pendientes. Su consulta individual y su idempotencia conservan el mismo codcom. No se modifica la migración histórica: la nueva redefine únicamente la función de listado necesaria y amplía el CHECK de estado.

La cantidad identificada se calcula contando las unidades vinculadas; pendiente = cancom - cantidad identificada. No hay contador persistido ni incremento de cantidad comprada. La única fuente de cantidad declarada es `factura_compra.cantidad_motos`: POST de identificación solo recibe `unidades`. Una factura de 4 motos permite un lote de 2 y luego otro de 2. Aceites y otras bonificaciones no se envían como unidades ni se incluyen en ese número.

Una compra puede estar en `Pendiente de identificación` y estar bloqueada por una discrepancia de factura. La RPC compara siempre `factura.cantidad_motos` con `compra.cancom`; si difieren devuelve `PT411` sin crear unidades, independientemente del frontend o de `requiere_revision`. No se añade otro estado.

Al actualizar una instalación con la firma anterior, reaplicar esta migración revisada en el entorno correspondiente: retira `hu002_identificar_unidades(bigint,integer,jsonb)` y conserva solo `hu002_identificar_unidades(bigint,jsonb)` con sus permisos. Desplegar conjuntamente API y migración; las herramientas que ya registraron la migración como aplicada no la ejecutarán automáticamente otra vez.

Los datos históricos sin metadatos de factura no se reinterpretan como facturas recibidas. Al vincular información real, el estado se sincroniza con las fichas existentes. Nunca se inventa una factura para migrar.

## Endpoints

Todos requieren `Authorization: Bearer <access_token>` y rol Gerente o Administradora activos. El Vendedor conserva la consulta comercial de HU-034, sin acceder a factura o series por estos endpoints.

| Método | Ruta | Resultado |
|---|---|---|
| PUT | /api/compras/:id/factura | Registrar metadatos de factura recibida, 200 |
| POST | /api/compras/:id/unidades | Identificar lote completo o revertirlo, 201 |
| GET | /api/compras/:id/unidades | Consultar factura, fichas identificadas y cantidad pendiente, 200 |

No se añade GET /api/unidades/:id. Un duplicado retorna una proyección segura de la ficha en el 409.

PUT factura:

```json
{
  "emisor": "Emisor que aparece en la factura",
  "numero": "F001-123",
  "fecha_emision": "2026-10-01",
  "cantidad_motos": 4
}
```

Reenviar los mismos metadatos es idempotente y conserva codfac. Datos diferentes para una factura ya vinculada devuelven 409; no se sobrescribe. Si la cantidad declarada difiere de cancom, se registra la recepción del documento con `requiere_revision: true` y un mensaje explícito; no cambia la cantidad comprada ni crea unidades. La identificación queda bloqueada hasta revisar y corregir el dato equivocado mediante un procedimiento administrativo autorizado. No se implementa un flujo de corrección de documentos fuera del alcance de esta HU.

POST unidades:

```json
{
  "unidades": [
    { "nummotuni": "MOTOR-REAL-1", "chauni": "CHASIS-REAL-1", "codmod": "1", "coluni": "Azul" },
    { "nummotuni": "MOTOR-REAL-2", "chauni": "CHASIS-REAL-2", "codmod": "1", "coluni": "Azul" }
  ]
}
```

Los ejemplos se sustituyen por datos reales del documento o datos ficticios de QA; no se generan series en la API. El lote admite de 1 a 100 motos y el cuerpo conserva el límite global de 32 KB. La normalización de series agrupa espacios, quita espacios exteriores y pasa a mayúsculas; no elimina guiones ni signos. Se comprueba modelo exacto y color normalizado contra la compra. Cantidad positiva entera, motor/chasis no vacíos de hasta 100 caracteres, color de hasta 50. Se rechazan campos adicionales y valores operativos.

POST y GET retornan `data` con codcom, cantidad_comprada, cantidad_identificada, cantidad_pendiente, estcom, factura y unidades. La lista contiene todas las unidades de la compra, incluidas las anteriores, para que el frontend conozca qué falta. Los identificadores BIGINT se devuelven como cadenas. Un reenvío del mismo lote ya guardado devuelve conflicto por series existentes; consultar antes de reintentar. Nunca se sobrescribe una ficha ni se crea una copia.

Errores: 400 entrada inválida; 401 sesión ausente/vencida; 403 rol no permitido; 404 compra inexistente; 409 duplicado, discrepancia, exceso, factura diferente o ausente. El 409 por serie existente incluye `conflicto.campo` y `conflicto.unidad` con ID, compra, modelo, motor, chasis, color y fecha; no expone notas privadas. Los conflictos dentro del propio lote pueden no incluir una ficha persistida. Los errores internos se traducen sin exponer SQL.

## Integridad y concurrencia

La función de identificación bloquea la fila de compra antes de leer su cantidad y el número de fichas existentes. Las operaciones simultáneas sobre esa compra se serializan. Los triggers de inserción/cambio de identificación y eliminación usan esa misma fila; no se puede superar cancom insertando directamente en PostgreSQL. Otro trigger impide reducir cancom por debajo de las fichas existentes y bloquea cambiar los datos originales de una compra ya facturada o identificada sin revisión.

Los índices únicos normalizados protegen motor y chasis incluso entre compras distintas. Los bloqueos transaccionales de series se toman en orden determinista para los lotes; el trigger también comprueba series existentes. Un conflicto o error revierte todo el lote. Se prueba expresamente un error en la segunda inserción, después de que la primera haya pasado las validaciones.

La escritura de unidad y factura se realiza por RPC autorizado; no se conceden permisos de tabla a authenticated o anon. RLS restrictivo impide que una política permisiva anterior lo eluda. Las funciones privadas no son ejecutables por clientes. Otros módulos futuros deben integrar operaciones autorizadas, no reabrir escritura directa.

Los permisos y checks de HU-026 siguen vigentes. La identificación no escribe ubicación, preparación, techo, proveedor, separación ni venta; conserva el default previo `No disponible` al crear la ficha, sin marcarla disponible. Las fichas ya registradas no se actualizan; sus compromisos y datos operativos permanecen. No se crean placeholders ni se admite cambiar codcom de una ficha.

## Contratos y arquitectura

Todos los contratos reutilizables están en `src/types/unidad.types.ts`, incluidos factura, entrada normalizada, solicitud de lote, resultado, consulta y conflicto. Services y validaciones importan esos contratos con `import type`; no usan ReturnType ni definen contratos reutilizables anónimos. Controllers gestionan HTTP; reglas se validan en utils y PostgreSQL; services ejecutan RPC.

## QA

Importar `HU-002.postman_collection.json`. Configurar URL de API, proyecto, clave anon y credenciales localmente; usar un modelo existente. La colección permite crear una compra QA de dos motos, registrar los metadatos, identificar la primera y completar la segunda tras iniciar sesión como Administradora. Cambiar las series por otras ficticias únicas para cada ejecución nueva. Para otra compra, vaciar idempotencia_compra. No exportar tokens ni contraseñas.

Pruebas automatizadas: sesiones y roles, metadatos/estados, compra inexistente, lote parcial y final, discrepancias de modelo/color/cantidad, duplicados dentro del lote y entre compras, no superar cancom, errores directos de BD, rollback intermedio, conservación de datos operativos/separación, pendientes de HU-034, reaplicación y regresión HU-026/HU-034.

Las pruebas SQL usan PostgreSQL embebido PGlite y las migraciones reales; las pruebas HTTP simulan la conexión a Supabase. PGlite no ejecuta conexiones PostgreSQL independientes. Antes de cerrar QA, probar dos solicitudes simultáneas con lotes distintos cuando queda una sola plaza: solo una debe crear unidad, la otra debe recibir 409. Probar también la misma serie simultánea en compras distintas: solo una debe persistir, sin duplicados. Esta comprobación y los tokens reales deben verificarse en el Supabase de QA; no se ha modificado la base remota.

La aceptación completa queda pendiente de la carga física de factura, la verificación integrada en QA y la validación del equipo.
