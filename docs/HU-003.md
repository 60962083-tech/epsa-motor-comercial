# HU-003 — Registrar movimientos de ubicación

## Alcance implementado

El backend registra la salida física hacia una ubicación activa y conserva `unidad.codubi` como la última ubicación confirmada mientras la unidad está en tránsito. La recepción confirma el destino, finaliza el movimiento y actualiza la unidad en la misma transacción. El movimiento no modifica estado comercial, separación, venta, preparación ni configuración de techo.

Las unidades sin ubicación confirmada no se pueden mover. HU-003 no asigna Crossland Ancón durante la identificación: esa asignación corresponde a HU-030.

## Migración y trazabilidad

La nueva migración es `supabase/migrations/202610190001_hu003_movimientos_ubicacion.sql`. No modifica las migraciones anteriores. Antes de crear el índice de un movimiento activo por unidad, comprueba si hay más de uno; si los encuentra, aborta con un mensaje para revisión manual y no elimina filas.

La migración agrega estos campos a `movimientoubicacion`:

| Columna | Uso |
|---|---|
| `codusurec` | FK al usuario que confirma la recepción |
| `fecrecmub` | Fecha de recepción según la base de datos |
| `horrecmub` | Hora de recepción según la base de datos |

Los tres campos permanecen NULL mientras `estmub='En transito'`. Al finalizar una recepción nueva, la RPC guarda los tres junto con `estmub='Finalizado'`. Los movimientos históricos que ya estaban `Finalizado` conservan esos campos en NULL: no se inventa un autor ni una fecha de recepción pasada.

Se conserva el CHECK de estados existente. HU-003 crea movimientos nuevos como `En transito` y los finaliza como `Finalizado`; no añade una operación para `Pendiente` ni una ruta de cancelación. El índice parcial `uq_movubicacion_unidad_activa` cubre `Pendiente` y `En transito` para impedir más de un movimiento activo.

## RPC y seguridad

- `hu003_iniciar_movimiento(p_coduni, p_codubiori, p_codubides, p_obsmub)` bloquea la unidad, compara el origen esperado, valida ubicaciones activas y registra la salida con usuario y hora de base de datos.
- `hu003_confirmar_recepcion(p_coduni, p_codmub)` bloquea unidad y movimiento, comprueba que sigue en tránsito y que la unidad conserva el origen, registra receptor/fecha/hora y actualiza `unidad.codubi` al destino en una transacción.
- `hu003_consultar_movimientos(p_coduni)` devuelve ubicación confirmada, movimiento activo e historial ordenado por fecha, hora e ID descendentes.
- `hu003_proyeccion_movimiento(p_codmub)` es una proyección interna usada por las RPC anteriores; no tiene EXECUTE para los clientes.

Las RPC usan `SECURITY DEFINER`, `SET search_path = ''` y validan en PostgreSQL que el usuario y rol estén activos. Solo `authenticated` recibe EXECUTE sobre las tres RPC públicas. La migración revoca acceso directo a la tabla y su secuencia, habilita RLS y añade una política restrictiva que deniega acceso directo. No se concede SELECT sobre `usuario`; la proyección incluye solo el nombre básico del autor, sin correo ni otros datos.

## Endpoints

Todas las rutas requieren `Authorization: Bearer <access_token>`.

| Método | Ruta | Roles |
|---|---|---|
| `POST` | `/api/unidades/:coduni/movimientos` | Gerente, Administradora |
| `PATCH` | `/api/unidades/:coduni/movimientos/:codmub/recepcion` | Gerente, Administradora |
| `GET` | `/api/unidades/:coduni/movimientos` | Gerente, Administradora, Vendedor |

POST acepta exactamente:

```json
{
  "codubiori": "4",
  "codubides": "5",
  "obsmub": "Traslado para instalación de techo"
}
```

Los códigos son cadenas BIGINT positivas. `obsmub` se puede omitir o enviar como texto o null. No se aceptan `codusu`, `fecmub`, `hormub`, `estmub` ni otros campos. El backend y la base de datos resuelven autor, fecha/hora y estado.

La recepción no requiere cuerpo. Rechaza cualquier campo enviado por el cliente; usuario, fecha y hora se resuelven en la RPC.

POST responde `201`, PATCH y GET responden `200`. Inicio responde con `message` y una proyección en estado `En transito`:

```json
{
  "ok": true,
  "message": "Movimiento iniciado; la unidad conserva su ubicación confirmada",
  "data": {
    "codmub": "12",
    "coduni": "20",
    "origen": { "codubi": "4", "nomubi": "Crossland Ancón" },
    "destino": { "codubi": "5", "nomubi": "FIVESA" },
    "estado": "En transito",
    "fechaSalida": "2026-10-19",
    "horaSalida": "09:30:00",
    "autorSalida": { "nombre": "Gerente QA" },
    "fechaRecepcion": null,
    "horaRecepcion": null,
    "autorRecepcion": null,
    "observacion": "Traslado para instalación de techo"
  }
}
```

Al confirmar la recepción, `data` tiene la misma estructura, pero `estado` es `Finalizado` y `fechaRecepcion`, `horaRecepcion` y `autorRecepcion` vienen informados. La respuesta incluye:

```json
{
  "ok": true,
  "message": "Recepción confirmada; la ubicación de la unidad fue actualizada",
  "data": {
    "codmub": "12",
    "coduni": "20",
    "origen": { "codubi": "4", "nomubi": "Crossland Ancón" },
    "destino": { "codubi": "5", "nomubi": "FIVESA" },
    "estado": "Finalizado",
    "fechaSalida": "2026-10-19",
    "horaSalida": "09:30:00",
    "autorSalida": { "nombre": "Gerente QA" },
    "fechaRecepcion": "2026-10-19",
    "horaRecepcion": "10:15:00",
    "autorRecepcion": { "nombre": "Administradora QA" },
    "observacion": "Traslado para instalación de techo"

```

Los códigos y marcas de tiempo del ejemplo son ilustrativos y no deben fijarse en frontend. GET devuelve `movimientoActivo` como la proyección completa anterior (o `null`) y cada elemento de `movimientos` con la misma estructura:

## Errores

- `400`: cuerpo, código o origen/destino inválido.
- `401`: token ausente, inválido o vencido.
- `403`: usuario/rol inactivo o Vendedor intenta iniciar/recibir.
- `404`: unidad, movimiento o ubicación inexistente.
- `409`: origen obsoleto, unidad sin ubicación confirmada, movimiento activo existente, destino inactivo, recepción repetida o conflicto de concurrencia.
- `500`: error interno con respuesta controlada, sin detalles de SQL.

## Verificación y límites

Las pruebas HTTP y PGlite cubren rutas, roles, estados, origen/destino, tránsito, recepción, trazabilidad, preservación de estados independientes, permisos directos y preflight de duplicados. PGlite ejecuta la migración localmente; no sustituye una prueba con conexiones concurrentes reales en Supabase QA.

La pantalla de inventario existente sigue usando estado local del navegador. Esta entrega no modifica frontend ni lo conecta a estas rutas. Antes de aplicar la migración en QA, revisar los movimientos `Pendiente` preexistentes: se conservan y bloquean nuevos traslados de esa unidad, pero HU-003 solo confirma recepciones en `En transito`.
