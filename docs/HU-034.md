# HU-034 — Backend de compras pendientes

Registra modelo, color y cantidad después de cotizar/pagar a Crossland. Conserva una compra provisional con autor, fecha, hora e identificador automáticos, sin crear unidades físicas, números de motor/chasis ni disponibilidad de entrega.

## Instalación e integración

1. Usar la rama `feature/HU-034-compra-pendiente`, basada en HU-026. No se sustituye su implementación.
2. Aplicar primero la migración de HU-026 y después `supabase/migrations/202610040001_hu034_compra_pendiente.sql` en el SQL Editor del proyecto de QA, con permisos administrativos.
3. La nueva migración amplía la tabla existente: añade `idempotencia` UUID con índice único, comprueba color no vacío y expone funciones protegidas. Las compras previas conservan sus datos y clave null; los nuevos registros vía API requieren clave.
4. Si ya existen colores vacíos, la migración revierte. Corregir esos datos con información confirmada; no inventar colores. La migración puede reaplicarse.
5. Usar las mismas variables `.env` de HU-026 y las cuentas reales de Supabase Auth vinculadas a `usuario.uuidusu`. Ejecutar `npm ci`, `npm run dev`. Pruebas: `npm test`; compilación: `npm run build`.

La API necesita la nueva migración antes de desplegarse. Ninguno de los scripts de pruebas se conecta a Supabase. No se requiere una clave service_role, Asiri ni integración con facturas/correo.

## Contrato HTTP

Todas las rutas requieren `Authorization: Bearer <access_token>`. Se conserva la respuesta `{ ok, data, message? }` del proyecto.

| Método y ruta | Propósito | Perfiles activos |
|---|---|---|
| POST /api/compras | Registrar o reintentar una compra | Gerente, Administradora |
| GET /api/compras?limite=50&offset=0 | Listar compras pendientes, más recientes primero | Gerente, Administradora, Vendedor |
| GET /api/compras/:id | Consultar una compra para continuar sobre el mismo identificador | Gerente, Administradora, Vendedor |

POST requiere `Content-Type: application/json` y `Idempotency-Key: <UUID>`.

```json
{"codmod":"1","colcom":"Azul","cancom":3}
```

El modelo debe existir; no necesita estar publicado en el catálogo público para ser comprado. No se crea un módulo de modelos: se reutilizan los registros del equipo/HU-012. `codmod` acepta una cadena numérica positiva o un entero seguro; las cadenas permiten representar BIGINT sin pérdida de precisión.

Color: texto obligatorio de hasta 50 caracteres, normalizado eliminando espacios exteriores y agrupando espacios repetidos. Cantidad: número entero de 1 a 2147483647, nunca cadena ni decimal. Campos adicionales se rechazan, incluidos autor, fecha, estado, motor o chasis. Los errores HTTP de validación señalan el campo incorrecto.

Respuestas: 201 para compra nueva; 200 para reintento idéntico o consulta; 400 datos inválidos/modelo inexistente; 401 sesión ausente o inválida; 403 perfil no permitido; 404 compra inexistente; 409 clave reutilizada con otros datos o autor. Un fallo interno responde 500 sin detalles privados.

La lista tiene límite por defecto 50, máximo 100, offset mínimo 0; si no hay pendientes devuelve `[]`. Los identificadores de compra, modelo y autor se devuelven como cadenas para preservar BIGINT.

## Estado y continuidad con HU-002

HU-034 crea la compra en `Pendiente de factura`. Al aplicar HU-002, registrar los metadatos de la factura recibida cambia a `Pendiente de identificación`; solo al completar todas sus unidades pasa a `Identificada`. El listado de pendientes incluye ambos estados pendientes. Consultar `docs/HU-002.md` para el contrato de identificación y el alcance pendiente de la carga del archivo.

La respuesta comercial contiene `codcom`, `codmod`, `nommod`, `colcom`, `cancom`, `cantidad_pendiente`, `estcom`, `feccom` y `horcom`. Para gerente/administradora añade `codusu`; no expone observaciones privadas, documentos ni la clave de idempotencia. `cantidad_pendiente` es la cantidad comprada menos las unidades ya vinculadas, con mínimo cero: indica identificación pendiente, nunca disponibilidad de entrega.

HU-002 debe recibir el mismo `codcom` para registrar sus unidades y actualizar el estado cuando corresponda. HU-034 no crea un endpoint ficticio de completar ni implementa identificación. Tampoco confirma recepción física ni entrega. La consulta individual sigue funcionando cuando la compra pasa a `Identificada`; deja entonces de aparecer en el listado de pendientes.

## Autor, seguridad y acceso a datos

La BD obtiene el autor mediante `auth.uid()` y la relación con usuario; verifica usuario y rol activos reutilizando `hu026_rol_actual`. Asigna fecha/hora del registro en America/Lima y fuerza el estado inicial. La API no acepta valores del cliente para estos campos.

La tabla compra no queda accesible directamente a anon ni authenticated. Se habilita RLS, se revocan accesos directos y se añade una política restrictiva, para evitar que otras políticas permisivas permitan saltarse autor automático, reintentos o privacidad. Solo las funciones públicas de esta historia tienen permiso de ejecución para authenticated; comprueban roles internamente. El helper de proyección es privado.

HU-002 deberá implementar sus propias operaciones autorizadas/transaccionales para completar compras. No se debe devolver acceso libre a la tabla ni reutilizar una clave privilegiada en el frontend. Esta migración no cambia usuario, rol, unidad, ubicación ni las funciones/políticas de HU-026.

## Reintentos y respaldo de la administradora

El frontend genera un UUID por intención de compra y lo conserva hasta obtener una respuesta inequívoca. Un reintento por pérdida de conexión debe usar la misma clave y los mismos datos; así devuelve la misma compra, incluso si después fue identificada. Una nueva compra requiere otra clave, aunque coincidan modelo, color y cantidad.

La clave es única globalmente. Reutilizarla con datos distintos o desde otro usuario da 409 sin revelar la compra original. La función usa un bloqueo transaccional por clave y un índice único; validación, búsqueda e inserción forman una sola operación SQL. Las compras distintas nunca se fusionan por modelo/color.

La administradora debe consultar pendientes antes de registrar una compra omitida. El backend proporciona el listado; el frontend y QA deben incluir ese paso. No se puede deducir que dos compras con claves distintas sean la misma compra real: confirmar con el gerente antes de ingresar el respaldo. HU-002 debe conservar modelo, color y cantidad originales para mantener el contrato del reintento.

## Pruebas con Postman

Importar `HU-034.postman_collection.json`. Completar localmente URL de API, URL/clave anon de Supabase, correo, contraseña y un codmod existente. Iniciar sesión; el token queda en la colección. No exportar credenciales ni tokens a Git.

La petición de registro genera una clave solo si la variable `idempotencia` está vacía. Volver a enviarla prueba el reintento. Para una compra distinta, vaciar esa variable y reenviar. Al cambiar de usuario para probar a la administradora, usar una clave nueva. Se guarda `codcom` para consultar el detalle.

| Escenario | Comprobación |
|---|---|
| 1. Registro mínimo | 201; ID, autor de sesión, fecha/hora automáticas, estado pendiente |
| 2. Datos inválidos | Falta modelo/color, cantidad 0/negativa/decimal/texto, modelo inexistente: rechazo sin alta |
| 3. Sin motor/chasis | Registro válido sin esos campos; cero unidades nuevas; enviar series da 400 |
| 4. Consulta comercial | Modelo/color/cantidad pendiente separados; vendedor sin autor ni datos privados; no stock disponible |
| 5. Reintento y respaldo | Mismo UUID/datos/autor: mismo ID y 200; UUID con datos distintos: 409; nueva clave: compra distinta; administradora revisa pendientes |
| 6. Continuidad | Detalle por mismo ID disponible para HU-002, sin Asiri ni automatización |
| Permisos | Vendedor no registra; anon no consulta; usuario/rol inactivo no accede; tampoco se elude vía tabla directa |

## Verificación y entrega

Las pruebas HTTP usan Supabase simulado; las pruebas SQL ejecutan el esquema original y ambas migraciones en PostgreSQL embebido (PGlite). Comprueban reintentos, validaciones, autor, privacidad, continuidad y conservación de datos existentes. Se ejecutan también las pruebas de HU-026. PGlite no prueba conexiones concurrentes independientes ni tokens reales; falta la validación integrada en Supabase QA, incluida la repetición simultánea de una misma clave.

El PR debe dirigirse a develop según el flujo del equipo. Como la rama incluye HU-026 todavía pendiente de revisión, el diff contra develop puede mostrar ambas historias hasta que HU-026 se integre; identificar esa dependencia en la descripción, sin reescribir ni eliminar su base.
