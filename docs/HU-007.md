# HU-007 — Autenticación y permisos del backend

La implementación conserva Supabase Auth, el cliente de Supabase por petición y la protección existente de HU-026 y HU-034. Añade autorización reutilizable y una identidad explícita obtenida de la base de datos. No depende de HU-002 ni introduce roles o funcionalidades comerciales nuevas.

## Despliegue

Aplicar `supabase/migrations/202610070001_hu007_permisos_rol.sql` después de las migraciones HU-026 y HU-034 y antes de desplegar el middleware actualizado. La migración añade únicamente `hu007_usuario_actual()` y sus permisos; puede reaplicarse y no modifica tablas, datos, RLS ni funciones de las historias anteriores.

La nueva función reutiliza `hu026_rol_actual()` para validar el usuario y el rol activos. No retirar esa función: sigue siendo utilizada por las políticas RLS y RPC de HU-026/HU-034. No se necesita ejecutar ninguna migración de HU-002.

La actualización de la API depende de la nueva función. Si no se ha aplicado la migración, la comprobación de identidad falla y no concede acceso. No usar service_role ni desactivar RLS para evitar ese error.

## Flujo de identidad

1. La petición presenta `Authorization: Bearer <access_token>`.
2. `autenticar` valida el token con `db.auth.getUser(token)`; no confía en un JWT simplemente decodificado.
3. Con el mismo token, llama a `hu007_usuario_actual()` sin parámetros. PostgreSQL obtiene `auth.uid()` y devuelve únicamente codusu, uuidusu y rol del usuario activo.
4. Se comprueba que el UUID devuelto coincida con la identidad validada por Supabase Auth y que el rol sea Gerente, Administradora o Vendedor.
5. El contexto de la petición recibe `res.locals.usuario` con el contrato `UsuarioAutenticado`, `res.locals.db` con el cliente autenticado y `res.locals.rol` por compatibilidad.

No se usa rol, codusu o UUID del body, query, cabeceras personalizadas ni user_metadata como fuente de permisos. No se almacena el perfil entre peticiones: una desactivación o cambio de rol se consulta de nuevo. Las RPC/RLS siguen verificando permisos dentro de PostgreSQL al ejecutar las operaciones.

Los usuarios presentes en Supabase Auth pero ausentes de la tabla usuario no tienen acceso. Tampoco lo tienen usuarios inactivos, roles inactivos o nombres de rol fuera de la HU. Las credenciales, el login y la renovación del token siguen gestionándose mediante Supabase Auth; esta entrega no añade una pantalla ni otro mecanismo de login.

## Autorización reutilizable

Importar `autenticar`, `exigirRoles` y `exigirGestion` desde `src/middleware/autenticacion.ts`. Usar primero `autenticar` y después el middleware de autorización en la ruta protegida.

- `exigirRoles('Gerente', 'Administradora')` permite exactamente esos roles.
- `exigirRoles('Gerente', 'Administradora', 'Vendedor')` permite los tres roles definidos.
- `exigirRoles()` no permite ninguno.
- `exigirGestion` comparte la misma lógica y conserva el mensaje: **Solo gerente y administradora pueden realizar esta operación de gestión**.

Los contratos de identidad y rol se definen en `src/types/autenticacion.types.ts` y se importan con `import type` donde corresponda. La autorización comprueba el usuario validado de `res.locals.usuario`, no un rol tomado del cliente.

No usar un codusu libre del frontend para atribuir acciones. En futuras operaciones, tomar la identidad del contexto validado o derivarla en PostgreSQL mediante auth.uid(), como ya hace HU-034. Un permiso por rol no reemplaza restricciones de propiedad: cuando se implemente cancelar una operación propia, esa pertenencia deberá comprobarse también en BD. Esta entrega no crea esos endpoints ni anticipa su lógica.

## Matriz de las rutas existentes

| Operación | Gerente | Administradora | Vendedor |
|---|---|---|---|
| GET /api/ubicaciones | Sí | Sí | Sí |
| POST /api/ubicaciones | Sí | Sí | No |
| PUT /api/ubicaciones/:id | Sí | Sí | No |
| PATCH /api/ubicaciones/:id/estado | Sí | Sí | No |
| GET /api/compras | Sí | Sí | Consulta comercial segura |
| GET /api/compras/:id | Sí | Sí | Consulta comercial segura |
| POST /api/compras | Sí | Sí | No |

La raíz informativa de la API conserva su comportamiento. No se añaden operaciones de unidades, ventas, separaciones, devoluciones, preparación, recepción ni emisión de comprobantes. Las reglas específicas descritas en EMT-12 para esas operaciones deberán aplicarse cuando exista su implementación.

## Respuestas de rechazo

- 401: token faltante, malformado, inválido o vencido.
- 403: usuario/rol inexistente, inactivo, no autorizado o sin permiso para la operación. También se rechaza una identidad de BD que no corresponda al token validado.
- 500: fallo técnico al verificar identidad; no se concede acceso ni se devuelve el detalle de SQL, token o credenciales.

Un enlace directo al endpoint está sujeto a las mismas comprobaciones que una solicitud realizada desde los botones del frontend. Las funciones RPC tampoco aceptan parámetros para seleccionar la identidad de otro usuario.

## Pruebas

`npm test` ejecuta la suite completa. `npm run build` compila el backend.

Las pruebas nuevas verifican token ausente/inválido, rol permitido, ausencia de perfil, usuario o rol inactivo, nombres de rol no autorizados, falsificación de rol/autor, combinaciones de exigirRoles, denegación por defecto, mensaje de exigirGestion, identidad separada en peticiones simultáneas y fallo de BD sin filtración de detalles.

Las pruebas PostgreSQL locales cargan solo el esquema base y las migraciones HU-026/HU-034/HU-007. Verifican la identidad propia, permisos de ejecución, reaplicación, conservación de hu026_rol_actual, autor real de las compras y rechazo en BD tras desactivar una cuenta. Los tests HTTP anteriores mantienen sus aserciones; únicamente se actualiza la respuesta simulada de la consulta de identidad.

La suite usa clientes simulados para HTTP y PostgreSQL embebido PGlite para SQL. No modifica Supabase. Tras aplicar la migración en QA, probar las rutas existentes con tokens reales de las tres cuentas y con una cuenta desactivada. No guardar tokens o contraseñas en Git.
